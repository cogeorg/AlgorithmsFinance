# 实验方法与复现

实验在个人作业目录内运行，使用 Python 标准库。正式测量在单个工作进程中串行执行；时间、逐事件延迟、内存、操作计数分开运行。两版源文件不因测量而修改。

## 运行与资源限制

```sh
python3 -B -m unittest discover -s tests -v
python3 -B benchmark.py --smoke --out work/smoke_results
python3 -B benchmark.py --out results/benchmark --phase-limit 5 --rss-mib 512
```

完整实验包含五个场景、事件数 1,000／10,000／100,000、种子 42／43／44，共 90 个“版本 × 场景 × 规模 × 种子”组合。每个组合保存五次原始计时；超限时仍保留该次尝试，不填造缺失结果。另尝试一组种子 42 的百万事件 mixed 输入。

每个输入解析、引擎回放、逐事件延迟或 tracemalloc 阶段的墙钟上限为 5 秒。每个子进程的 RSS 预算为 512 MiB。RSS 守护线程约每 100ms 检查 `resource.getrusage(...).ru_maxrss`，发现超限立即终止进程；采样有延迟，不能保证内存从未瞬间超过预算。守护线程带来小幅后台开销，两版均启用。另有较宽松的整工作进程 watchdog，防止准备或输出阶段卡住。

最初的监督器尝试使用 `ps`，环境禁止进程检查，未进入正式实验；该准备阶段记录留在忽略的 `work/initial_benchmark_ps_restriction/`。正式结果统一采用进程自报 RSS，代码指纹记录在 settings 中。

相同参数重复运行会按完成的 job 恢复；若源文件指纹或关键设置改变则拒绝混入旧数据，应改用新的输出目录。未完成 job 会重新测量。操作系统可能存在其他后台活动，未控制 CPU 频率或温度，因此结果是这台机器上的观测，不是硬件无关常数。

## 输入与代码版本

`generate_orders.py` 原样复制自作业包，完全独立于撮合实现。每个输入先生成到 `work/benchmark_inputs/`，生成时间不计入引擎时间。`input_manifest.json` 保存种子、规模、价格范围、生成命令、压缩字节数和 SHA-256。

常规生成参数为每侧1,000个可用价格；crowded场景按生成器定义始终使用每侧4个价格，即使命令传入levels=1000。实际占用价格峰值另有记录。输入生成和元数据回放已经读过文件，未清空操作系统页缓存，因此解析测量不能代表冷盘读取性能。

`work/` 被本作业的 `.gitignore` 排除，包含百万事件文件在内的生成数据不会进入提交。依靠生成器、命令和校验和复现输入。

`settings.json` 记录 Python、操作系统、CPU/内存信息、依赖、源代码 SHA-256、Git 基础提交及精确命令。用户要求不 commit，因此本阶段的实际代码版本由 SHA-256 指纹标识；基础提交本身不包含尚未提交的作业代码。

## 时间

每版先在独立订单簿上预热相同输入的前 1,000 个事件（小输入则用全部），丢弃该订单簿。正式每次重复重新读取同一已生成文件，并创建新的空订单簿。

- `input_parse`：gzip 解压、文本读取和 JSON 解析为事件列表。
- `replay`：空簿创建、完整事件循环、撮合/状态更新/返回 fill 构造，以及最小的已处理事件和 fill 计数。使用 `time.perf_counter`。不在计时中做簿检查、哈希、断言、打印、延迟分位数或内存追踪。
- `construction`：buildup/crowded 完整回放，或 sweep 前 80% 被动建簿的计时检查点。检查点来自同一个连续 replay，属于它的前缀，不能与 replay 相加。
- `parse_plus_replay`：同一次重复的已测解析时间加回放时间，明确是两段计时的和；不冒充含进程启动、诊断检查和 JSON 输出的 CLI 墙钟时间。

计时上下文的信号定时器设置/撤销及上述少量循环 bookkeeping 在测量边界内；这会在特别小的样本中产生可见固定开销。最终排序快照与正确性哈希在计时之后执行。

完整回放的吞吐量为 M/replay秒数。超时只记录完成前缀，不计算“完整吞吐量”。中位数默认使用所有完成重复；若不足五次，summary 明确标记 `median_is_censored_subset=true`，不能与五次完整结果等同。原始停止尝试仍在 raw 表内。

## 延迟

另开工作进程，预热后用新的空簿，分别在每个 `process_event` 调用前后读取 `perf_counter`。保存全部逐事件时间到 `latency/*.csv.gz`；汇总总体、事件类型，以及原始流前 10%／后 10%。长批次不主动暂停或插入打印。

median 对偶数个值取中间两值平均；P95/P99 用 nearest-rank，即升序后取 `ceil(p*n)-1` 下标，不插值。超时 run 只包含已完成事件前缀，并明确标记；若尚未进入原始流末段则不报告 late 分布。

时间戳写入样本数组等 bookkeeping 在逐事件计时之外，但会影响下一事件缓存和调度；这是带仪表的算法处理延迟，不包含网络或排队，也不能据此判断真实市场的过载速率。不能用吞吐量倒数代替尾延迟。

## 内存

另开工作进程，在预加载事件之后开启 tracemalloc，再创建空簿和回放。记录峰值 traced bytes，并在第 1／2 个事件及每 10% 位置保存当前/峰值字节与活跃订单数。读取时保留当前事件返回结果；不保存整个成交历史。

测量包含引擎新分配的簿结构、记录、当次输出及很小的探针记录缓冲；不包含 tracemalloc 开启之前分配的输入对象及其共享字符串。输入在进程中真实存在，只是其旧分配不计入增量 trace。RSS 预算则覆盖整个进程，包括输入和 tracemalloc 本身。

RSS守护线程在追踪期间的少量瞬时分配也可能进入tracemalloc读数，不能将这些字节全部归因于订单记录。

取消频繁场景的最终当前字节数用于观察撤单后状态，插入场景的分段读数用于观察增长。Python 容器可能保留历史容量，分配器也可能缓存空间；traced allocations 不是理论辅助空间，也不是总进程/native 内存。

## 活跃深度与操作诊断

独立、未计时的 B 版工作负载回放，结合外部的订单残量/价格计数器计算精确 B/P 峰值与 fill 总数。外部计数器与最终规范订单簿核对。计时行将峰值注明为此独立工作负载元数据，避免为每次计时回放插入重度计数。所有完成的 A/B 计时与仪表运行还核对最终簿哈希。

小型随机流和五个官方样例已另有逐事件等价证据；正式大型运行的最终簿哈希检查不替代那些测试。可选百万事件尝试若能完成但没有参考哈希，会明确标记，不能宣称已完成等价验证。

操作诊断对每个场景 seed42 的前 200 个事件进行 Python 行追踪，统计两版真实执行行次数及对应源代码；与正式时间/延迟/内存完全分开。它是小诊断，不将前缀计数外推为全部工作负载的运行成本。

## 大额卖出与价格集中度

固定买单数 N=1,000／10,000／100,000，seed42，分别使用 4／1,000 个可用价格，生成相同的被动买单流。初始价格/数量固定于该组合，与版本无关。每个版本先通过真实事件创建原始买盘模板，单独保存构建成本。

每次卖出先 `deepcopy` 未被修改的模板，单独测量 reset；因此不复用已耗尽的簿，也没有把复制当免费。模板只构建一次，其成本与每次 reset/sell 结果分开，不能误读为每次都重建全部事件。

分别卖出可用数量 10%／100%／200%，10% 使用整数向上取整且至少一单位。每个数量预热一次，正式重复五次；sell 时间包含撮合、状态更新及 fill 列表构造。返回结果与独立的“按价格/FIFO排序后逐项取量”的预期逐笔核对。记录 maker 数、访问价格数、fills 和未成交量。

构建或复制超限时，相关 sale 明确记为未运行，不能报告一个不存在的 sale 时间。固定 N 的 4/1,000 档结果可用于分析长队列；模板设置的 available levels 与实际占用档数分别看配置和结果。

## 结果文件

- `raw_results.jsonl`：所有阶段、重复、停止原因、内存探针与行计数，完整原始主表。
- `raw_results.csv`：适合表格工具和后续仪表盘的标量列。
- `summary.json`：分版本/场景/规模/种子/阶段的中位数和完成次数。
- `latency/*.csv.gz`：全部逐事件时间，而非仅分位数。
- `jobs/`：每个独立进程的配置、原始 stdout 和 stderr。
- `settings.json`、`input_manifest.json`：环境、边界、命令与输入指纹。
