Limit order book: baseline versus revision

Saved measurements of two Python implementations of a sequential, single-venue BTC limit order book on synthetic teaching data. Version A keeps each side as an unsorted list and scans it. Version B keeps a FIFO queue per price, a heap of prices per side and an order index. Changing a view filters the saved data; nothing is measured again. This is a teaching model, not a production trading system.

    1 · Submission flood and full streams

    Replay time as the stream grows

    Median of five replays of the selected workload family, each on a fresh empty book. Engine time only: reading and parsing the file are measured separately and listed in the table. Both axes are logarithmic.

    B = active orders, P = occupied price levels (both at their peak during the stream), F = maker fills. A stream with more events does not need a larger book: compare cancel_churn with buildup. "Application" adds the separately measured read-and-parse median to the replay median.

    2 · Book construction

    Construction: time inside one stream

    Cumulative engine time at every 5% of the selected stream (median of five replays). A straight line means constant cost per event; a curve that bends upward means later events cost more because the book has grown.

    3 · Large liquidation and queue concentration

    One large market sell against a fresh bid book

    Each trial builds a new one-sided book of N bids over the stated number of prices and then sells the selected share of its total quantity once. The clock covers matching, state updates and building the fill list; construction is timed separately. Median of five trials; no trial reuses a depleted book.

    Queue concentration: same order count, different number of prices

    With one price every maker waits in a single queue; with 1,000 prices queues are short and many levels are visited. Every completed sale is compared with a fill plan computed independently by sorting the bids by price and arrival.

    4 · Latency

    Processing latency per event

    Separate instrumented pass: perf_counter_ns around every dispatcher call for the selected stream. Percentiles use the nearest-rank convention. This is engine processing time only; it contains no network or queueing delay and says nothing about the load at which a live venue would fall behind. It is not the reciprocal of throughput.

    5 · Memory and cancellation churn

    Memory

    Separate pass under tracemalloc: bytes of Python allocations made by the book, its indexes and the most recent returned result. Preloaded input is excluded (streams above 100,000 events are parsed in blocks of 1,000 inside the trace). Neither version stores a trade history. Traced bytes are neither auxiliary space in the textbook sense nor the memory of the whole process.

    After cancellation: does anything keep growing?

    cancel_churn alternates one submission and its cancellation; mass_cancel builds a book and then cancels all but about 1% of it. "Stored entries" counts every slot the engine still holds (list or queue entries, index entries, price levels, heap entries).

    7 · Revision

    Second revision step: tuning version B

    Version B was first written with two side objects, one object per order and a chain of small validation calls (preserved as book_b1.py, "B1"). The submitted version B keeps the same data organization (FIFO queue per price, price heaps, order index) and removes constant-factor overhead; the shared event envelope was streamlined at the same time, which also benefits version A. tuning.py replays the same streams through all three engines in one process, interleaved repeat by repeat, after checking that every result is identical. "B1 original" is B1 behind the envelope as first written.
